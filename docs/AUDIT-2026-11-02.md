## 1. Verified bugs (fix first)

### B1. Last-admin guard has a check-then-act race — MEDIUM · verified

`src/server/modules/users/users.service.ts:151-158` — `assertAnotherActiveAdmin()` counts other active admins **outside** the `$transaction`; `setUserStatus` (line 174) and `deleteUser` call it before the transaction starts (line 176+). Two concurrent requests (the last two admins disabling/deleting each other) can both pass the check and both commit, leaving zero active admins — exactly what the guard exists to prevent.

**Fix:** move the count inside the transaction (`tx.user.count({ where: { id: { not: id }, status: "ACTIVE", role: "ADMIN" } })`) immediately before the `update`/`delete`, and return it in the tx body.

### B2. Rate-limit identity is keyed on a client-spoofable IP — MEDIUM (host-dependent) · verified

`src/server/core/request-context.ts:5-9` takes the **first** `x-forwarded-for` entry, which the _client_ sent unless a proxy overwrites it. On a custom Node/nginx deploy (the standalone output is built for exactly that), an attacker rotates `X-Forwarded-For` per request and (a) defeats the per-IP limit and (b) defeats the per-identity limit too, because the identity key embeds the IP (`signin:id:${ip}:${email}`, `auth.service.ts:24`). Spoofed values also land in `Session.ip` and `AuditLog.ip` (audit integrity). On Vercel the platform manages XFF, so production there is safe today — this bites the moment the standalone build is self-hosted (a stated deploy option).

**Fix:** derive the IP from the last trusted hop or the platform header (`CF-Connecting-IP` / `x-vercel-forwarded-for`), validate it parses as an IP, else `"unknown"`. Additionally, key the identity limit on the **email alone** (`signin:id:<email>`) so IP rotation can't reset it; keep the IP limit as the second check.

### B3. `.env.example` documents the wrong `NEXT_PUBLIC_SITE_URL` default — MEDIUM · verified

`.env.example:7` says "defaults to https://portfolio-mamun.vercel.app", but `src/env.ts:38-41` defaults to `http://localhost:3000`. A developer who deletes the line believing the prod URL is the fallback silently gets `localhost` canonicals, sitemap URLs, and JSON-LD `@id`s in production (README.md:83's exact warning).

**Fix:** change the comment to "defaults to http://localhost:3000; set the production URL at build time."

### B4. Sign-out never expires the session/dashboard cache tags — MEDIUM · verified

`auth.session.ts:110-123` (`revokeByToken`) and `auth.actions.ts:35-37` (`signOutAction`) revoke the Session row without expiring any tag, while every other session mutation declares tags. The account page's sessions list and the dashboard's active-session count stay stale until another mutation or the `cacheLife("admin")` timers lapse (up to 24 h, `next.config.ts`).

**Fix:** call `expireTags([CACHE_TAGS.sessions(userId), CACHE_TAGS.DASHBOARD, CACHE_TAGS.AUDIT])` from `signOutAction` (it runs in a request scope) or from the Auth.js `signOut` event.

### B5. `accountTags.changePassword` omits `DASHBOARD` — LOW · verified

`account.constants.ts:3-8` lists `user:<id>`, `sessions:<id>`, `AUDIT` — but changing your own password revokes your _other_ sessions (`account.service.ts:46-53`), which changes the dashboard's active-session stat. `sessionTags.revoke`/`revokeAll` and all `userTags` entries include `CACHE_TAGS.DASHBOARD`; this one doesn't. One-line fix.

### B6. Root OG image can 500 on a long-running standalone server — MEDIUM · verified

`src/app/opengraph-image.tsx:16-23` reads the portrait with `path.join(process.cwd(), "src/assets/portrait-square.jpg")` inside `"use cache"; cacheLife("max")` (revalidate 30 days). The path is not statically analyzable, so file tracing may not ship `src/assets/` with the standalone output; when the cache entry revalidates on a server that has run >30 days, the read can throw ENOENT and take `/opengraph-image` down. Works at build time (cwd = project root), which is why nobody noticed.

**Fix:** `await readFile(new URL("../assets/portrait-square.jpg", import.meta.url))` (traced reliably), or move the portrait under `public/` and reference it by URL.

### B7. `useUrlState` composes rapid updates from stale params — MEDIUM · verified

`src/components/ui/use-url-state.ts:18-31` builds the next query from `useSearchParams()`, which only reflects the last **committed** URL. While a transition is in flight, a second `update()` (350 ms search debounce fires, then the user changes the status filter) is built from pre-navigation params and `router.replace` overwrites the first patch. Concretely: search "foo" starts navigating → user picks "Disabled" → committed URL has `status=DISABLED` but no `searchTerm`, and `SearchInput`'s render sync (search-input.tsx:33-37) visibly wipes what the user typed.

**Fix:** keep the latest intended params in a shared ref (updated synchronously in `update()`), and build from it instead of `useSearchParams()`. All list controls share `useUrlState`, so one fix covers search, filters, and pagination. Worth doing before the first real content module inherits this plumbing.

### B8. `FilterSelect` doesn't work without JavaScript — MEDIUM (consistency) · verified

`filter-select.tsx:23-43` is a bare `<select>` driven by `onChange`. `SearchInput` and `PerPageSelect` both degrade to `method="get"` forms; the Users "status" filter and Audit-log "area" filter silently do nothing without JS, breaking the codebase's own stated bar ("core flows work without client JS", ARCHITECTURE §10).

**Fix:** wrap in a GET form like `PerPageSelect`: hidden inputs preserving `searchTerm`/`sortBy`/`sortOrder`/`limit`, `name={param}` on the select, `<noscript>` Apply button.

### B9. Success handler lost when a form dialog closes mid-flight — MEDIUM-LOW · verified (reported; code read)

`action-form.tsx:67-69` runs `onSuccess` (the `router.refresh()` that updates the table) in the form's effect; `user-overlays.tsx` mounts the form only while the drawer/dialog is open. Pressing Esc while a create/edit/set-password submit is in flight unmounts the form before the effect runs: the mutation **is** applied server-side, but the table stays stale with no toast. (`useConfirmAction` dialogs don't have this problem — `ConfirmDialog` stays mounted.)

**Fix:** keep the form mounted until the pending transition settles, or hoist success handling to the overlay hook level like `useConfirmAction` does.

### B10. Session revoke/revokeAll write audit outside the transaction — LOW · verified (reported)

`sessions.service.ts:55-67, 78-88` — `update` then `writeAudit` with the global `db`, against AGENTS.md rule 6 (users/account services do it correctly with `tx`). Wrap both in `db.$transaction`.

### B11. `SEED_ADMIN_RESET` password reset leaves old sessions valid — LOW · verified (reported)

`prisma/seed.ts:44-55` sets a new `passwordHash` but doesn't revoke existing Session rows, and session validation doesn't compare `lastSeenAt` against `passwordChangedAt`. An operator who resets a forgotten password leaves any live session (up to 12 h) authenticated. Fix in the seed's update branch (`updateMany` sessions → revoked).

### B12. `assertSameOrigin` throws 500 on a malformed `Origin` — LOW · verified (reported)

`core/http/route.ts:84` — `new URL("null")` (sandboxed iframe) or any non-URL origin throws inside the handler and surfaces as `INTERNAL_ERROR` instead of 403, with log noise. Wrap in try/catch; treat unparseable origins as foreign.

### B13. No request-body size cap on Route Handlers — LOW · verified (reported)

`core/http/route.ts:89-96` — `await req.json()` with no `content-length` check; a single request can buffer an arbitrarily large body (memory DoS on `/api/users`). Reject > ~64 KB early.

### B14. Cover-art fake-UI text is exposed to screen readers — MEDIUM (a11y) · verified (reported)

`cover-art.tsx:13-29` (+ `cover-art-data.tsx`, `cover-art-scenes.tsx`) render terminal lines, `$` prompts, "queued"/"sending" badges as real text on every project card and the no-screenshot gallery. Screen-reader users get this noise everywhere; only the case-study gallery has the explanatory paragraph. **Fix:** `aria-hidden="true"` on the cover-art container, with a single sr-only "Illustration of the interface" label (keep the visible "illustration" chip outside it).

### B15. Case-study breadcrumb: JSON-LD ≠ visible trail — LOW · verified (reported)

`case-study-header.tsx:22-39` shows `projects / <slug>`; the JSON-LD (`page.tsx:52-56`) says `Home / Projects / <Title>`. Google wants them to match. Add the Home crumb and render the project title.

### B16. Small verified nits (one-liners)

- `robots.ts:6` disallows `/admin/` but not the exact `/admin` path (which redirects to sign-in). Add `"/admin"`.
- `jsonld.ts:105` uses `sameAs` for a live demo URL — wrong property semantics; drop it or use `subjectOf`.
- `profile.service.ts:96,104` computes a `technologies` stat nothing consumes — dead code.
- `experience-section.tsx:25` hard-codes "Four years" — the only non-derived duration in the UI; it will silently rot (the rest derive from `careerStart`).
- `pagination.tsx:79 vs 96` — Previous from page 2 yields redundant `?page=1` (numbered links strip it).
- `search-input.tsx:56-60` — Enter in the search box does a **full page reload** even with JS on (native GET submit not intercepted); add `onSubmit` → `preventDefault()` + `update()`.
- `confirm-dialog.tsx:65-90` — failure message not linked to the type-to-confirm input (`aria-describedby`), Cancel stays enabled while pending.
- `toast.tsx:16-40,71-76` — module-level store outlives the Toaster; auto-dismiss timers never cancelled → stale toasts can re-announce after navigating away and back within 4.5–8 s.
- `chat-panel.tsx:38-43` — auto-scroll uses `behavior:"smooth"` unconditionally; respect `motionAllowed()`.
- `user-menu.tsx:75-79` — sign-out menu item has no pending state; double-click fires twice (harmless, untidy).
- `audit-log/page.tsx:85` — parses a `sortOrder` param the table never uses.
- `env.ts:10,25` + `auth.session.ts:16-18` — stale comments reference `src/server/db.ts` / `src/server/auth.ts` / `dal/sessions.ts`, none of which exist.
- Missing `import "server-only"` on `core/errors/{codes,app-error,zod-error,prisma-error}.ts` and the three `*.constants.ts` files (AGENTS.md says every `src/server/**` file starts with it; `prisma-error.ts` imports the generated client).
- `auth.prisma` — no index on `Session.revokedAt` for the opportunistic cleanup query (`auth.session.ts:62-71`); free to add in the next migration.
- Blocked sign-ins write an AuditLog row per attempt (`auth.service.ts:65`) — combined with B2, IP rotation can insert unbounded audit rows; consider writing `auth.signin.blocked` only for the first block per window.

### Not a bug (checked and cleared)

- **The admin e2e suite does NOT trip the sign-in rate limit.** Superficially 4 sign-ins × 2 Playwright projects = 8 > `PER_IDENTITY = 5`, but `verifyCredentials` calls `reset(idKey)` after every successful sign-in (`auth.service.ts:104`), so successes never accumulate; the wrong-password test deliberately uses a throwaway address, and the shared IP key (limit 30) stays under. CI runs confirm green.

## 2. Known limitations → fix plans

From ARCHITECTURE.md's status table (⚠️/⬜ rows), plus open decisions carried from the pre-launch audit.

### K1. Contact is a `mailto:` hand-off — the biggest product limitation

Status: ⚠️ in ARCHITECTURE.md; known since the pre-launch audit, deferred as "owner's choice: no backend". It remains the primary conversion path with no delivery guarantee: no-JS submission depends on inconsistent `mailto:` form behavior (Chromium flags it as potential mixed content; silently does nothing with no mail handler), and the 1,200-char cap counts characters, not percent-encoded bytes (Bangla text expands ~9× and can blow past the ~2,000-char mailto ceiling).

**Plan (≈ 1 day):**

1. `Message` model in `prisma/schema/contact.prisma` (name, email, subject, body, ip, userAgent, status) → migration.
2. `src/server/modules/contact/` following the §14 recipe: zod schema (already exists in `lib/schemas/contact.ts`), service (`sendMessage` + `assertAdmin` reads), actions (`publicAction` — this one is public), controller; tags in `CACHE_TAGS`.
3. Email delivery through `src/server/email` (console transport in dev; Resend/Postmark in prod via one `EMAIL_*` env var validated in `env.ts` + `.env.example`).
4. Honeypot field + the existing DB rate limiter keyed on IP.
5. Contact form becomes `<ActionForm>` with real pending/success/error states; keep `mailto:` + Gmail/Outlook links + Copy email as the error/fallback state. No-JS path: progressive enhancement via the plain form POST.
6. Store every message; an admin "Messages" module (list, mark read) can follow the same recipe.
7. Byte-count the message cap (or lower it) so encoded mailto links stay under the ceiling.

### K2. CSP is report-only

Status: ⚠️ in ARCHITECTURE.md. `next.config.ts` ships `Content-Security-Policy-Report-Only` with `'unsafe-inline'` for scripts/styles.

**Plan (≈ half a day):** check production reports/console for violations → rename the header to enforcing → add `upgrade-insecure-requests` → consider a `report-uri` endpoint or reporting service so regressions are visible. If true nonce-based CSP is wanted later, it needs per-request rendering (proxy.ts) — a bigger change, only worth it if inline scripts grow.

### K3. Admin content modules (Projects, Blogs, Professions, Categories, Settings)

Status: ⬜ "Coming soon" pages. The recipe (§14) and the reference implementation (users) are ready; **fix B7/B8/B9 first**, because every new module inherits the list/form plumbing. Suggested order by product value: Projects → Professions (feeds the experience/skills UI) → Categories → Blogs (needs MDX/DB decision) → Settings (site-wide key/values). Each module: schema + migration → zod → module (model/service/constants/actions/controller) → routes with loading/error → nav entry (`status: "ready"`) → unit + e2e → status-table row. Budget ≈ 1–2 days per module.

### K4. Blog

Status: ⬜ planned; `/blog/*` currently 308s to `/`. The old post (Vue vs React) should be ported so its URL keeps working. Decide DB-backed (K3 recipe, `Blog` model + MDX body column) vs MDX files in-repo behind the same content-service seam. Add RSS (`feed.xml`) and `BlogPosting` JSON-LD when the first post lands.

### K5. `/llms.txt` — spec'd but missing

### K9. Three.js performance guard — intentionally open

Known from the pre-launch audit: on GPU-less machines the scene drops to 4–8 fps. A hard software-GL guard (`failIfMajorPerformanceCaveat`) was tried and **reverted at the owner's request** because it turned the background off on the owner's own machine. Keep as a documented decision. Middle path if it ever reopens: adaptive quality (drop particle count when frame time exceeds a threshold) rather than a hard skip.

## 3. Security hardening (beyond bugs)

1. **Actions pinned by tag, not SHA** — `.github/workflows/ci.yml` (`actions/checkout@v7.0.1` etc.). Pin to full commit SHAs (Dependabot keeps them updated); the job holds a Postgres service and `AUTH_SECRET`.
2. **Node version policy inconsistent** — `engines.node >=22.22.1`, `.nvmrc` = 24, `@types/node` ^22, Dependabot comment says "Node 22", CI runs Node 24 (via `.nvmrc`). Pick one: bump `@types/node` to ^24 and fix the comment, or pin `.nvmrc` to 22.22.1.
3. **`PASSWORD_MIN = 8`** (`lib/auth/password-params.ts:10`) vs ARCHITECTURE §11 "minimum length of 12" — doc/code disagree. Either raise to 12 (migration-free; schema change is a one-liner but forces existing-user password updates on next change only) or fix the doc.
4. **XFF hardening** — see B2.
5. **`useSecureCookies` derives from `NEXT_PUBLIC_SITE_URL`**, which defaults to http — a prod deploy that forgets the variable yields non-Secure cookies (trustHost then fails closed, so impact is contained). Consider a boot-time warning when `NODE_ENV=production` and the site URL is not https.
6. **Blocked-sign-in audit spam** — see B16 last item.

## 4. Test and CI gaps

1. **Split the CI job** — typecheck/lint/format/unit don't need Postgres; run them parallel to the build+e2e job so a lint typo doesn't pay for a full build+e2e cycle. Cache Playwright browsers (`~/.cache/ms-playwright` keyed on the `@playwright/test` lockfile version; ~130 MB re-downloaded every run today).
2. **Contact form has no e2e** — the site's primary conversion is only render+axe-checked. Add: invalid submit → field errors + focus moved; valid submit → intercept the `mailto:` navigation and assert subject/body; Gmail/Outlook links present; and the no-JS submission path.
3. **Light theme never tested** — axe only ever runs against the default dark theme. One test: click the toggle → `html.light`, persists across reload, `expectNoSeriousA11yIssues` on `/` and `/projects` in light mode.
4. **Untested security flows** — change own password (and sign back in with it), admin sets another user's password, revoke a session via the API. All audited mutations with cache invalidation.
5. **axe coverage is narrower than documented** — ARCHITECTURE.md:236 says "axe on every route, zero violations"; reality is serious/critical-only on some routes, and `/admin/account`, `/admin/users/[id]`, and the 404 page are never scanned. Either widen the policy or fix the doc.
6. **JSON-LD builders untested** — `jsonld.test.ts` covers only `serializeJsonLd` escaping + breadcrumb order; `personJsonLd`, `websiteJsonLd`, `profilePageJsonLd`, `projectJsonLd` have no `@type` assertions (ARCHITECTURE.md:181 claims otherwise).
7. **`?category=` filter untested** — README advertises it; no e2e asserts the URL param filters the cards.
8. **`mutation-tags.test.ts` is a regex tripwire** — line-format-sensitive; document the expectation or match `adminAction({` / `apiRoute({` with an `s` flag.
9. **Playwright config nits** — add `screenshot: "only-on-failure"`, a `test.setTimeout(120_000)` for the ~40-interaction serial admin test, `127.0.0.1` in the health-check URL (server binds `127.0.0.1`, config checks `localhost`, which can resolve to `::1`), and derive the `admin.spec.ts:58` cookie URL from `baseURL`.
10. **`capture-screenshots.ts`** — exits 0 on partial failure and always rewrites the manifest (easy to commit a half-updated set); desktop JPEGs are written before the combined assignment, so a mobile-stage failure leaves orphans; re-captures never delete stale shots; manifest key order isn't sorted. Track failures → non-zero exit with a summary; delete `public/projects/<slug>/*.jpg` files not in the new shot list; sort manifest keys.

## 5. Improvement roadmap (product)

Ordered by value to the two audiences in PRODUCT.md:

1. **Working contact pipeline** (K1) — conversion with a guarantee.
2. **Analytics with conversion events** — today there's no way to know whether anyone downloads the CV or reaches out. Privacy-friendly, cookieless (Vercel Web Analytics or Plausible): CV download, contact submit, WhatsApp click, case-study views. Speed Insights for real-user CWV. Requires the CSP `connect-src` addition (K2) and a `/privacy` note if anything sets cookies.
3. **HTML résumé at `/resume`** (or a print stylesheet for `/about`) — crawlable, ATS-friendly, always current; PDF stays as the download.
4. **Generated OG cards for `/about`, `/projects`, `/contact`** — the default card exists (`OgFrame` makes per-page cards cheap); the pages currently share the root card.
5. **Booking link** (Cal.com) next to "Email me" on `/contact` and the footer CTA for contract clients.
6. **Chatbot: build it or hide it** — it's still a placeholder answering "coming soon" in the most prominent spot on every page (the owner chose to keep it at pre-launch; that decision can be revisited now that launch is past). When built: one route handler streaming from a small model, grounded in `src/content/*` (fits in the prompt), per-IP rate limit, token cap, email/WhatsApp fallback; the `useChat` seam is already in place.
7. **Case-study depth** — an architecture diagram per production system; before/after numbers only where verifiable.
