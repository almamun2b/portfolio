# Home page performance plan (Lighthouse desktop 83 → 90+)

## Results (2026-10-23, all steps implemented)

Local production build (`node .next/standalone/server.js` on :3100), Lighthouse 13.5.0 desktop preset, headless Chrome. This machine has 4 cores and a load average of ~11 during the runs, so single runs swing widely. Compare medians, not single runs.

| Run                       | Score (median, range) | TBT          | Speed Index | "Other" main-thread |
| ------------------------- | --------------------- | ------------ | ----------- | ------------------- |
| Before (3 runs)           | **59** (56–71)        | 701–5,185 ms | 1.6–7.1 s   | 4.1–25.3 s          |
| After steps 1–5 (3 runs)  | **79** (78–82)        | 365–484 ms   | 1.3–1.4 s   | 0.75–1.2 s          |
| Final, all steps (5 runs) | **89** (81–99)        | 92–391 ms    | 0.6–1.2 s   | 0.5–0.8 s           |

Mobile (one run after the changes, no baseline taken): 69, with LCP 3.5 s and TBT 991 ms. Mobile LCP wasn't in scope here and is worth a separate look.

What made the difference: headless Chrome (Lighthouse and PageSpeed Insights) has no GPU, so WebGL falls back to SwiftShader and every constellation frame ran on the CPU. That was the multi-second "Other" bucket. The constellation now checks for hardware WebGL 2 (`failIfMajorPerformanceCaveat`) **before** downloading three.js, so software-GL visitors (and lab tools) get the CSS glows and never fetch the 136 KB chunk. Visitors with a GPU still get the scene after their first interaction or ~4 s after load. The remaining TBT is React hydration (framework chunk + app entry).

Changes against the plan below:

- Card `sizes` became `(min-width: 1600px) 28rem, (min-width: 1280px) 24rem, …`. The container widens to 90rem at 1600px, so a single 23rem value would undersize there.
- The hardware-WebGL pre-check in `background.tsx` was added on top of `failIfMajorPerformanceCaveat` in `scene.ts`, so three.js isn't even downloaded when it would be refused.
- Step 6: `WidgetTip` moved to `src/components/widgets/widget-tip.tsx`, and `SocialIcon` inlines its paths, so no client component imports the `simple-icons` barrel. The dev server no longer loads a simple-icons chunk.

### Local dev run (`next dev` on :3000, Lighthouse 13.5.0 desktop, 2026-10-23)

Score **59**: FCP 0.4 s, LCP 1.0 s, **TBT 5,290 ms**, SI 8.1 s, CLS 0, TTI 19.6 s. Dev mode is dominated by dev-only cost (unminified `react-dom` development build, HMR client, next-devtools 249 KB), so it can't be the benchmark. It does confirm two things:

- **three.js init is a 237 ms long task** (`three.core`, starting ~5.1 s). That's the step 1 target.
- **`simple-icons` ships its whole 2.1 MB barrel in dev** and causes a 410 ms long task. It's imported from client code (`whatsapp-button.tsx`, `social-icon.tsx`, `src/lib/tech.ts`). Production tree-shakes it (no such chunk on the live site), so users don't pay it, but it slows every dev reload. See step 6.

## Steps

### 0. Save this plan to `docs/` and take a local baseline

- Copy this file to `docs/PERF-PLAN-2026-10-23.md`, next to `docs/AUDIT-2026-10-21.md`.
- Get a **local Lighthouse baseline before any change**, then re-run it after each step (1, 2, 3) so every win is attributed. Run Lighthouse against the **local production build** (`pnpm build && pnpm start` on :3000, run in the background), not `pnpm dev`. Dev-mode bundles are unminified and include React Refresh and dev overlays, so dev scores are meaningless for TBT and unused JS. If a `pnpm dev` is already holding :3000, start the prod server on another port (`PORT=3100 pnpm start`).
- Command (desktop preset, matching the report the user shared; 3 runs, take the median): `pnpm dlx lighthouse http://localhost:3100/ --preset=desktop --only-categories=performance --output=json --output-path=<scratchpad>/lh-<step>.json --chrome-flags="--headless=new"`, using the Playwright-cached Chromium via `CHROME_PATH` if no system Chrome is found. Also do one mobile run (default preset) for reference.
- Record the score, TBT, SI and the top long tasks in a before/after table in the docs file.

### 1. Constellation: start later, init in small chunks (biggest TBT win)

`src/components/effects/constellation/background.tsx`

- Start trigger: the **first user intent** (`pointermove`, `pointerdown`, `keydown`, `wheel`, `touchstart`, or `scroll`, once and passive) **or** a fallback of ~4 s after `load` (via `requestIdleCallback` with that timeout). Whichever comes first wins. Keep the Save-Data skip and the cleanup.
- Keep `import("./scene")` dynamic. Optionally add `<link rel="prefetch">`-style warming on intent only; a plain dynamic import is enough.

`src/components/effects/constellation/scene.ts`

- Make `createConstellation` async and **yield between phases** so no single task tops 50 ms. Use a small `yieldToMain()` helper: `scheduler.yield` when available, otherwise `setTimeout(0)`.
  1. Create the renderer (WebGL context). Yield.
  2. Build particles, links and shapes. Yield.
  3. `await renderer.compileAsync(scene, camera)` (three ≥ r158, uses `KHR_parallel_shader_compile`), so shader compilation leaves the main thread. Yield.
  4. Do the first render, then `canvas.dataset.ready = ""` and `play()`.
- Guard every phase against unmount (keep the `cancelled` flag; return a dispose that works mid-init).
- Update the doc comment ("loaded only after the page is idle" becomes "after first interaction or ~4 s").

### 2. Remove hydration-time forced reflows

- `src/components/ui/sliding-indicator.tsx`: drop the synchronous `measure()` call in the layout effect. The `ResizeObserver`'s initial callback (it fires on `observe()`, after layout, before paint) does the first measurement with no forced reflow. Move `revealActive()` into that first callback. Keep the `fonts.ready` re-measure. The SSR fallback (active item paints its own background until `data-indicator="ready"`) already covers the frame before the first measure, so there's no visual regression.
- `src/components/ui/stat-counter.tsx`: replace the `getBoundingClientRect()` "already on screen" check with the IntersectionObserver's **first** entry. If the first callback reports the element already intersecting (or above the viewport, `boundingClientRect.top < 0`), keep the server-rendered value and disconnect. Otherwise set `"0"` and animate on the next intersection. Note: setting `"0"` moves from the effect into the observer callback, so a counter far below the fold shows the real value until it is observed. That's fine, because it's off-screen.
- `src/components/effects/smooth-scroll.tsx`: create Lenis inside `requestIdleCallback` (`setTimeout` fallback), so its dimension reads leave the hydration task.

### 3. Stop re-blurring moving elements every frame

Replace `backdrop-filter` with an opaque-enough tinted background **only on elements that move or span the full width**. Static glass (header, cards, nav pill) stays, so the uniqtrix look is kept.

- `portrait-orbit.tsx` orbit chips: swap `glass` for `bg-[color-mix(in_srgb,var(--card-solid)_82%,transparent)]` (the same recipe the pills already use).
- `floating-pills.tsx`: drop `backdrop-blur-md`. The 78% `card-solid` mix already carries it.
- `tech-marquee.tsx`: drop `backdrop-blur-sm` and raise the background mix from 55% to ~80%.
- Check both themes visually (dark and light) at desktop and 375 px. If a chip reads too flat, raise the mix percentage rather than restoring the blur.

### 4. Inline the Lenis stylesheet (removes one render-blocking request)

- Remove `import "lenis/dist/lenis.css"` from `smooth-scroll.tsx`.
- Paste its 5 rules into `src/app/globals.css` under a short comment ("from lenis/dist/lenis.css v1.3; re-check on a Lenis bump").

### 5. Right-size project card images

- `src/components/projects/project-card.tsx:38`: `sizes="(min-width: 1280px) 23rem, (min-width: 768px) 45vw, 92vw"`. 23rem = 368 px, so the browser picks 384w at DPR 1 and 750w at DPR 2.
- Check the other card `sizes` strings (`filtered-projects` grid uses the same card, so it's covered).

### 6. (DX, optional) Keep the simple-icons barrel out of dev client bundles

- Client components shouldn't import from the `simple-icons` barrel. Move the few client-needed marks (WhatsApp, and anything `TechIcon`/`SocialIcon` render inside client components) into a small generated map of `{ title, path, hex }`, or render them as server components that pass the SVG path down as a prop. Check `src/lib/tech.ts` import sites to see which client components pull it in.
- Verify: re-run Lighthouse on `next dev` and confirm the `simple-icons_index_mjs` chunk is gone. Production output must be unchanged.

### 7. Docs

- ARCHITECTURE.md Implementation status: note the constellation's new start policy if the table mentions it.
- DESIGN.md: record that moving or full-width elements use a tinted background, not `glass`, for performance.

## Not doing (and why)

- **Replace three.js with raw WebGL / 2D canvas** (-136 KB). Worth it only if TBT is still >150 ms after step 1. Treat it as a separate follow-up.
- **`experimental.inlineCss`**: FCP is already 0.3 s. Inlining 18 KB into every HTML response defeats CSS caching across routes.
- **Next polyfill-module (14 KB)**: not configurable in Next 16, and unscored.
